# Linux Log Management and OpenSearch — Study Notes

## 1. Why Logs Matter

Logs are not just random lines of text. They are a **detailed historical account of every action, event, or error** that happens within your system.

### Why Log Management is Critical

- **Diagnose** system and application issues
- **Detect** unauthorized access and suspicious activity
- **Ensure** compliance and audit readiness
- **Support** forensic investigations
- **Enable** proactive maintenance before failures occur
- It is a **business necessity**, not just a technical task

### Real-World Failures from Poor Logging

| Failure | Root Cause |
|---|---|
| Data breach missed | Authentication logs were disabled |
| Web server crash with no clue | Error logging was not configured |
| Disk filled to 100% | Log files were never rotated |

---

## 2. What is Log Management?

Log management is the **full process of handling log messages** — collecting, storing, rotating, and analyzing them.

> "It's not just about collecting logs — it's about **structuring** them."

### The Log Management Cycle

```
1. Log Collection and Archiving
          ↓
2. Log Normalization (Structuring)
          ↓
3. Analysing / Monitoring / Alerting
          ↑_________________________|
```

## 3. Linux Logging Architecture

### Types of Logs in Linux

| Log Type | Description |
|---|---|
| **System Logs** | General OS activity, hardware messages, daemons starting/stopping |
| **Authentication Logs** | Login attempts, SSH access, sudo usage, password changes |
| **Kernel Logs** | Messages from the Linux kernel |
| **Daemon Logs** | Specific to background services like cron or systemd |
| **Application Logs** | Generated by user-space apps (nginx, MySQL, etc.) |
| **Package Manager Logs** | Software installs, removals, updates (apt/yum/dnf) |
| **Audit Logs** | Security-relevant events |
| **Boot Logs** | Useful for troubleshooting failed startups |
| **Systemd Journal** | Binary format logs accessed via `journalctl` |

### Logging Systems Used in Linux

| System | Description |
|---|---|
| **syslog** | Older, plaintext, modular |
| **rsyslog** | Enhanced version of syslog with more features |
| **journald** | Binary format, systemd-native, structured, advanced filtering |

### Typical Logging Path

```
Application → /dev/log → rsyslog → /var/log/
       OR
Application → systemd → journald → journal file (or forwarded to rsyslog)
```

### `/var/log` Directory Structure

| Path | Purpose |
|---|---|
| `/var/log/messages` or `/var/log/syslog` | General system logs |
| `/var/log/auth.log` or `/var/log/secure` | Authentication logs |
| `/var/log/kern.log` | Kernel messages |
| `/var/log/nginx/`, `/var/log/mysql/` | Application/service logs |

### Log Entry Format

```
<timestamp> <hostname> <process>[pid]: <message>
```

**Example:**
```
Jun 11 10:43:29 linux-training systemd[1]: apache2.service: Failed with result 'exit-code'.
```

## 4. Log Levels and Facilities

### Log Severity Levels (Syslog)

Syslog defines **8 severity levels**, from most to least critical:

| Code | Name | Meaning |
|---|---|---|
| 0 | **Emergency** | System is unusable |
| 1 | **Alert** | Immediate action required (e.g., disk full) |
| 2 | **Critical** | Critical conditions (e.g., memory errors) |
| 3 | **Error** | Errors needing attention |
| 4 | **Warning** | Potential issues or unexpected behavior |
| 5 | **Notice** | Normal but significant conditions |
| 6 | **Informational** | Routine operational information |
| 7 | **Debug** | Detailed information for debugging |

### Log Facilities

Facilities specify the **type or origin** of the log message:

| Code | Facility | Description |
|---|---|---|
| 0 | kern | Kernel messages |
| 1 | user | User-level processes |
| 2 | mail | Mail system |
| 3 | daemon | System daemons (systemd, cron) |
| 4 | auth | Security/authorization |
| 5 | syslog | Internal syslog messages |
| 6 | lpr | Line printer subsystem |
| 7 | news | Network news subsystem |
| 8 | uucp | Unix-to-Unix Copy system |
| 9 | cron | Clock daemon |
| 10 | authpriv | Security/authorization (private) |
| 11 | ftp | FTP daemon |
| 16–23 | local0–local7 | Custom use by applications/services |

## 5. Log Rotation and Retention

### What is `logrotate`?

`logrotate` is a utility that **manages the size of log files** automatically. It can:

- Rotate logs **daily, weekly, or monthly**
- **Compress** old logs (e.g., `.gz` format)
- **Retain** logs for a specified number of cycles
- Run **post-rotation scripts**
- Work with both system and application logs

### Log Retention Policy Guidelines

| Log Type | Typical Retention Period |
|---|---|
| System logs | 1–4 weeks |
| Security logs | 3–12 months |
| Compliance logs | 1–7 years (depends on regulations) |

## 6. Troubleshooting with Logs

Use this **methodical 8-step approach** when diagnosing issues:

```
Step 1 → Define the Problem Clearly
Step 2 → Identify Relevant Log Sources
Step 3 → Correlate with Time of Incident
Step 4 → Look for Obvious Errors
Step 5 → Trace the Workflow
Step 6 → Use Contextual Fields (host, PID, service)
Step 7 → Check Logs of Dependent Services
Step 8 → Verify Recovery
```

## 7. Centralized Logging

### Problems with Decentralized Logging

- Complexity in log aggregation and analysis
- Inconsistent log formats and standards
- Higher operational overhead
- Scattered security controls
- Limited real-time monitoring and alerting
- Data redundancy and inefficiency

### Why Centralize Logs?

| Benefit | Description |
|---|---|
| Simplified Troubleshooting | All logs in one searchable place |
| Improved Security Monitoring | Correlate events across systems |
| Compliance | Meet audit and regulatory requirements |
| Backup & Retention | Centralized retention policies |
| Automation | Trigger alerts and actions automatically |
| Performance Management | Monitor system health holistically |

### Centralized Logging Architecture

```
Log Sources
(Linux, Apps, Containers, Cloud, Network Devices)
         ↓
Log Collectors / Shippers
(Fluent Bit, Filebeat, rsyslog)
         ↓
Processing & Transformation
(Parse, normalize, enrich, add metadata)
         ↓
Storage & Indexing
(Shard by service/environment, apply ILM for retention)
         ↓
Visualization & Analysis
(Dashboards, monitors, alerts)
```

### Common Centralized Logging Solutions

- **ELK Stack** — Elasticsearch + Logstash + Kibana
- **OpenSearch Stack** — Open-source alternative (Apache 2.0)
- **Graylog**
- **Fluentd + Elasticsearch + Kibana**
- **Splunk** (commercial)

## 9. Log Shippers and Processors

### Tool Comparison

| Tool | Best For | Environment Example |
|---|---|---|
| **Logstash** | Complex parsing and enrichment before indexing | Centralized log processing clusters |
| **Filebeat** | Lightweight log shipping from many nodes | Cloud servers, edge devices, VMs |
| **Fluentd** | Highly customizable, multi-destination routing | Enterprise hybrid/multi-cloud setups |
| **Fluent Bit** | Lightweight agent in containerized/K8s setups | Kubernetes, Docker, IoT devices |

### Logstash Pipeline

```
Inputs → Filters → Outputs
```

```hcl
input {
  beats { port => 5044 }
}

filter {
  grok {
    match => { "message" => "%{COMBINEDAPACHELOG}" }
  }
  geoip {
    source => "clientip"
  }
}

output {
  elasticsearch {
    hosts => ["http://localhost:9200"]
    index => "weblogs-%{+YYYY.MM.dd}"
  }
}
```

### Filebeat Configuration Example

```yaml
filebeat.inputs:
- type: log
  paths:
    - /var/log/syslog

output.opensearch:
  hosts: ["http://localhost:9200"]
```

### Fluent Bit Pipeline

```
Input → Parser → Filter → Buffer → Output
```

- **Input:** Gather logs from sources
- **Parser:** Convert unstructured → structured messages
- **Filter:** Modify records, enrich records
- **Buffer:** SQL Stream Processing, Aggregations
- **Output:** Elasticsearch, OpenSearch, Kafka, Splunk

## 10. Introduction to OpenSearch

OpenSearch is a **distributed, open-source search and analytics engine** forked from Elasticsearch 7.10 by Amazon in 2021.

### Key Facts

- **License:** Apache 2.0 — no license fees
- **Designed for:** Full-text search, log analytics, anomaly detection, visualization
- **Alternative to:** ELK Stack (when cost or licensing is a concern)

### OpenSearch Stack Components

| Component | Role |
|---|---|
| **OpenSearch** | Search engine and indexing |
| **OpenSearch Dashboards** | Visual UI (equivalent to Kibana) |
| **Logstash / Filebeat** | Log shippers to feed data in |

## 11. OpenSearch Architecture

### Cluster

- A **logical grouping of nodes** working together
- Identified by a shared **cluster name**
- Manages and distributes data and workloads
- Enables scalability and high availability

### Node Types

| Node Type | Role |
|---|---|
| **Cluster Manager (Master) Node** | Controls cluster state and metadata |
| **Data Node** | Stores and retrieves documents |
| **Ingest Node** | Preprocesses and transforms data before indexing |
| **Coordinator Node** | Routes client requests to appropriate nodes |

> Nodes can have **multiple roles** or be specialized for performance.

### Indices

An **index** is a logical container for documents — similar to a table in a relational database.

```json
{
  "name": "Peter David",
  "designation": "Systems Engineer",
  "joined_date": "25-06-2020"
}
```

- Index mappings define **field types**
- Search and analytics queries run **on indices**

### Shards and Replicas

| Concept | Description |
|---|---|
| **Shard** | A subdivision of an index |
| **Primary Shard** | The original data holder |
| **Replica Shard** | A copy of a primary shard for redundancy |

- Enable **parallelism and failover**
- Improve **performance and fault tolerance**

```
Index
├── Shard 1 (Primary) → doc_1, doc_2
└── Shard 2 (Primary) → doc_3, doc_4

Node 01: Shard 1 Primary + Shard 2 Replica
Node 02: Shard 2 Primary + Shard 1 Replica
```

### Index Health Status

| Color | Meaning |
|---|---|
| 🟢 **Green** | All primary and replica shards active. Fully operational. |
| 🟡 **Yellow** | All primaries active, but some replicas are missing. Common on single-node clusters. |
| 🔴 **Red** | One or more **primary shards** are unallocated. Data unavailable. **Urgent attention needed!** |

## 13. Index Lifecycle Management

OpenSearch provides **Index State Management (ISM)** and **Index Lifecycle Policies (ILP)** to automatically manage log data over time.

### Index Phases

| Phase | Description |
|---|---|
| **Hot** | Recent logs, high-frequency queries, frequent writes |
| **Warm** | Older logs, rarely modified, still queried for troubleshooting |
| **Cold** | Archived logs, rarely queried, compressed |
| **Delete** | Remove logs after the retention period ends |

### Rollover Triggers

OpenSearch supports automatic rollover based on:

- Index **size**
- Number of **documents**
- **Age** of the index

## 14. High Availability and Scalability

### High Availability Best Practices

- Use a **minimum of 3 master nodes** to prevent split-brain issues
- Distribute **data nodes across availability zones**
- Use **snapshot repositories** for backup and disaster recovery
- Use **coordinating nodes** to offload query traffic from data nodes

### Scalability Best Practices

- Optimize the **number of shards per index**
- Monitor the **indexing rate** (logs ingested per second)
- Improve **query performance** — use filters, avoid wildcard searches
- Use **hot-warm-cold architecture** — fast storage for recent logs, cheaper storage for older logs

### Production-Level Architecture Example

```
Private Data Center
  App Servers + DB Servers + Firewall
        ↓ (Beats → TLS Encrypted)
  Logstash Server (parse & enrich)
        ↓
  AWS OpenSearch Service (VPC)
    ├── AZ-1: Master Node 01, Hot Node 01, Warm Node 01
    ├── AZ-2: Master Node 02, Hot Node 02, Warm Node 02
    └── AZ-3: Master Node 03, Hot Node 03, Warm Node 03
        ↓
  OpenSearch Dashboards (Kibana)

AWS EKS (Kubernetes)
  → Fluentd → TLS → Internet Gateway → Logstash
```

## 15. Security in OpenSearch

OpenSearch includes a **built-in Security Plugin** that provides:

| Feature | Description |
|---|---|
| **Fine-Grained Access Control (RBAC)** | Control who can access which indices and actions |
| **TLS Encryption** | Encrypts data both in transit and at rest |
| **User & Role Management** | Create users, assign roles and permissions |
| **Audit Logging** | Track all access and changes for compliance |
| **SSO Support** | Integrate with LDAP, SAML, or AWS Cognito |
